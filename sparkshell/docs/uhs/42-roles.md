# 42 人评审团：v3.4.0 的逐条意见

不是"角色扮演式夸赞"。每人给一句**可被反驳的判断**，附立场。投反对票的照样记下来。

## A. 需求与用户（7）

| # | 角色 | 判断 |
|---|---|---|
| 1 | 产品负责人 | 3.4.0 只做两件：少打扰、看得见图。别的都往后排。 |
| 2 | 用户研究员 | "点两下就烦"是真实痛点；旧审批必然被"全部允许"绕过，等于没有。 |
| 3 | 交互设计师 | 弹窗标题必须是原因（"要格式化分区"），不是工具名 `bash`。 |
| 4 | 文案 | 设置项叫"看图模型（可选）"，不叫"Vision Model"，用户不懂那个词。 |
| 5 | 新手用户代表 | 我永远不填看图模型，所以主流程必须在没填时也不报错。 |
| 6 | 重度用户代表 | 我要能一次放行整轮；"全部允许"保留，但只在危险弹窗里出现。 |
| 7 | 反对派（产品） | 反对：审批再怎么分级也是摩擦。**反驳**：不可逆动作没有第二次机会，摩擦买的是保险。 |

## B. 架构（7）

| # | 角色 | 判断 |
|---|---|---|
| 8 | 首席架构师 | 模型选择必须只有一个入口，`modelFor()` 是唯一真值，UI 不许自己拼。 |
| 9 | Agent 架构师 | 审批挂在 agent 循环入口，覆盖 bash / 写文件 / ssh，而不是散在工具内部。 |
| 10 | 平台工程师 | `modelOverride` 用可空参数透传，null 就是老行为，零回归风险。 |
| 11 | Dart 工程师 | 纯函数优先：`approvalFor()`、`modelFor()` 不依赖 context，能单测。 |
| 12 | 配置工程师 | 老配置文件缺 `visionModel` 必须读成空串；`catch(_)` 兜底不许吞掉迁移错误。 |
| 13 | 性能工程师 | 22 条正则每次调用线性扫，单次 < 1 ms，不值得预编译缓存。 |
| 14 | 反对派（架构） | 反对：规则表放代码里，用户改不了。**反驳**：可改的规则=可被模型诱导改，先固定。 |

## C. 实现（7）

| # | 角色 | 判断 |
|---|---|---|
| 15 | 后端工程师 | `curl|sh` 与 `base64|sh` 必须拦，这两条是 90% 的"手滑装马"。 |
| 16 | Shell 专家 | `rm -rf /root/build` 不拦：容器内、可重建，拦了就是噪音。 |
| 17 | 文件系统工程师 | 写 `/etc`、`/system` 才拦；相对路径落在 cwd，不拦。 |
| 18 | SSH 工程师 | `ssh_exec` 一律拦：命令跑在别人的机器上，本地规则看不见那边。 |
| 19 | UI 工程师 | `AlertDialog` 没有 subtitle，标题下直接放工具名 + 命令，别再踩一次。 |
| 20 | 测试工程师 | 13 条必拦、7 条必放、3 条路径判定、1 条截断，正反都要有。 |
| 21 | 反对派（实现） | 反对：正则挡不住 `rm -rf "$HOME"`。**反驳**：目标是挡手滑与幻觉，不是挡定向逃逸；逃逸由容器边界管。 |

## D. 安全与合规（7）

| # | 角色 | 判断 |
|---|---|---|
| 22 | 安全工程师 | 审批不是沙箱。容器仍是 `proot`，能碰到的只有 `/root` 与导入目录。 |
| 23 | 密钥管理员 | API Key 只进 `chat_config.json`（应用私有目录），不进 APK、不进日志。 |
| 24 | 隐私 | 图片只在带图那轮发出；`vision=false` 时只发路径，不发 base64。 |
| 25 | 供应链 | 依赖锁在 `pubspec.lock`；新增依赖要说明为什么不能自己写。 |
| 26 | 合规 | 不做设备控制（root/无障碍/ADB），避免把"聊天工具"变成"提权工具"。 |
| 27 | 审计 | 每个版本留 sha256 + CI run id，出了问题能追到构建。 |
| 28 | 反对派（安全） | 反对：`su` 规则在容器里无意义。**反驳**：无意义也要拦——用户可能把宿主命令贴进来。 |

## E. 验证（7）

| # | 角色 | 判断 |
|---|---|---|
| 29 | 测试负责人 | 沙箱跑不了 `flutter test`（无 git → SDK 0.0.0-unknown），门禁只能放 CI。 |
| 30 | 静态分析 | `flutter analyze` 当编译门禁，error 一律阻断发布。 |
| 31 | 回归 | 老路径必须零变化：`modelOverride == null` 时行为与 3.3.1 完全一致。 |
| 32 | 负对照 | 删掉 `--kill-on-exit`、删掉一条危险规则，检查必须变红。 |
| 33 | 真机 | 相机、相册多选、安装器拉起仍未真机验收，不许写成"已验证"。 |
| 34 | 度量 | 审批弹窗触发率应 < 10%；高于这个数说明规则太宽。 |
| 35 | 反对派（验证） | 反对：CI 绿≠能用。**反驳**：同意，所以交付里明确列出"未真机验收项"。 |

## F. 交付与运营（7）

| # | 角色 | 判断 |
|---|---|---|
| 36 | 发布经理 | 双包并行发布，`latest.json` 指向 Alpine（默认），Debian 单独给链接。 |
| 37 | SRE | VPS 只是中转；隧道换了域名就换，不写死在任何客户端里。 |
| 38 | 文档 | 每版 release notes 写"改了什么 + 依据是什么"，不写"优化体验"这种空话。 |
| 39 | 支持 | 用户报"点了没反应"，先看是不是 `_testing` 没转圈，再看网络。 |
| 40 | 成本 | 免费接入点 + 重试，不引入付费依赖；看图模型由用户自选、自付。 |
| 41 | 版本管理 | `app_version.dart` 单一真值，`pubspec.yaml` 跟随，测试守卫。 |
| 42 | 反对派（交付） | 反对：每版都更，用户会疲。**反驳**：所以合并成一批再发，不做一个改动发一版。 |

## 表决

- 赞成 34，保留 5（1、7、14、21、35 中的"保留意见"），反对 3（7、14、21 的原始立场，均被反驳但记录在案）。
- 唯一全票通过的结论：**不可逆动作必须问一次；其余不打扰。**
